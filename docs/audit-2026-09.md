# Maintenance audit — September 6, 2026

Scope: RunAcross 0.6.0 at `9d5127d`, all source modules, public interfaces,
tests and examples, packaging, documentation, GitHub workflows, repository
protections, release history, and installed dependency advisories. Changes
from this audit are delivered in 0.6.1.

## Assessment

The project has a useful, appropriately small scope: synchronous AWS account
and Region execution with explicit authentication and typed results. Keep
that scope. A CLI, async framework, workflow engine, or new runtime dependency
would increase maintenance costs without evidence of a corresponding need.

| Area | Assessment and action |
| --- | --- |
| Security | Existing least-privilege workflow permissions, pinned Actions, trusted PyPI publishing, and no credential persistence are sound. Remove automatic exception logging, clear nested exception tracebacks, and make export limitations explicit. |
| Correctness | Fix zero discovery limits and duplicate profile resolver calls. A resolver exception must fail only its target, and metadata must describe the selected profile. |
| Performance | Shared STS clients and per-account role reuse avoid unnecessary authentication calls. Bound pending futures; retain isolated callback Sessions and input ordering. |
| Utility | Keep two executor functions, explicit account sources, and export helpers. Add a practical operations guide rather than expanding the API. |
| Code quality | Baseline Ruff, strict mypy, and all 173 tests passed with 97.00% line coverage. Preserve explicit models; avoid a generic result-class rewrite merely to remove similar code. |
| Repository | Clean initial working tree, Apache-2.0 license, changelog, issue/PR templates, Dependabot, protected main and release tags. Secret scanning and push protection were enabled. |
| Delivery | Release builds previously skipped tests. Reuse CI on the release commit, preserve existing required check names, add job time limits, and treat release tag names as data. |
| Documentation | Existing examples and API overview are useful. Correct overly broad security claims, explain cancellation and memory limits, and make the roadmap prioritize stability. |

## Priorities and disposition

| Priority | Finding | 0.6.1 disposition |
| --- | --- | --- |
| P1 | A stateful profile resolver was called separately for metadata and authentication; an uncaught resolver error could abort the run. | Resolve once per attempt and store only selected profile metadata in thread-local state. Regression tests cover account and Region execution and worker reuse. |
| P1 | DEBUG logs included arbitrary exception text and tracebacks, potentially exposing application secrets. | Log execution metadata only. Original exceptions remain inspectable in results. |
| P1 | Exception groups could retain child tracebacks and callback locals. | Traverse grouped and chained errors, preserving exception types and clearing traceback references. |
| P1 | Releases could publish without tests for their commit; tag interpolation put event text directly into executable code. | Require reusable CI before build/publish and pass tags through environment variables. This is delivery hardening, not a claim of an unauthenticated remote exploit. |
| P2 | `limit=0` returned the first matching account. | Return no accounts and perform no config, credential, or inventory work after validating arguments. |
| P2 | An empty explicit Region selection still initialized authentication. | Return empty results before binding authentication, including when all Regions are excluded. |
| P2 | Eager submission allocated one Future per target; observer errors still allowed all queued work to execute. | Bound submissions to worker count, cancel unstarted work on interruption, and wait for running callbacks. |
| P2 | Tests could depend on a contributor's AWS config or accidentally reach AWS. | Isolate configuration and credentials and block Botocore HTTP transport during unit tests. |
| P2 | The declared Boto3 minimum and OS independence lacked dedicated CI coverage. | Add minimum-Boto3/Python 3.10 and Windows/Python 3.14 jobs. |
| P3 | Security/export claims and operational guidance needed precision. | Update security policy, API docs, contribution/release process, navigation, and operations guide. |

## Validation and measurements

The local suite after the fixes passes **189 tests** with **97.09% line
coverage** on Python 3.14.7/macOS. Ruff and strict mypy pass. `pip-audit`
reported **no known vulnerabilities** in the installed environment on the
audit date. This checks published advisories for that environment, not every
dependency version allowed by the package's lower bounds.

The reproducible `benchmarks/pool.py` comparison uses 20,000 trivial targets,
10 workers, and the median of three runs with `tracemalloc`:

| Scheduler | Peak traced memory | Elapsed time |
| --- | ---: | ---: |
| Eager 0.6.0 algorithm | 37.1429 MiB | 0.2379 s |
| Bounded 0.6.1 pool | 0.8237 MiB | 0.2965 s |

The sample reduces scheduler peak memory by about **97.8%**, with about
**25% more scheduling time for empty work**. That tradeoff is appropriate for
the library's network-bound use case, but it does not prove improved AWS
latency or throughput. Returned payloads and targets still require O(N) memory.
No production AWS accounts were queried or modified by this audit.

## Remaining work, in order

1. Add SDK Stubber coverage for real credential-provider and service-response
   integration boundaries, supplementing the current small fakes. Real IAM
   and Identity Center integration needs an explicitly provisioned sandbox.
2. Measure representative paginated AWS workloads before tuning worker defaults
   or introducing streaming results. Evaluate repeated failed role assumptions
   across many Regions if real throttling data justifies failure caching.
3. Improve callback/progress typing and invalid async-callback diagnostics
   without broadening the synchronous API. Validate packaging and signatures
   against real downstream consumers before declaring stable 1.0 compatibility.
4. Consider selectors or credential-refresh support only when actual use cases
   justify the additional API and security maintenance. Hard thread timeouts
   remain out of scope because running callbacks cannot be forcibly cancelled.

## Limits and references

This is a source and maintenance audit, not a penetration test or a guarantee
that vulnerabilities do not exist. Application callbacks, user-configured
credential processes, downstream IAM permissions, and arbitrary result data
remain outside the library's trust boundary.

- [Boto3 Session concurrency guidance](https://docs.aws.amazon.com/boto3/latest/guide/session.html)
  supports keeping callback Sessions isolated.
- [Python executor shutdown semantics](https://docs.python.org/3/library/concurrent.futures.html)
  distinguish cancellation of queued futures from completion of running work.
- [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use)
  recommends immutable action references, minimal token permissions, and
  environment variables for untrusted event data used by scripts.
